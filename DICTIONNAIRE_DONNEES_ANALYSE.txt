================================================================================
DICTIONNAIRE DES DONNEES — ANALYSE DU BACKEND
Projet : Compta-main — Gestion digitalisee de la comptabilite matieres
Date de l'analyse : 4 novembre 2026
Périmètre : backend/ uniquement (Strapi 5.53.0 + SQLite)
================================================================================

Ce document est une ANALYSE factuelle du backend, destinée à construire le
dictionnaire des données d'un mémoire de licence. Il décrit :
  - toutes les collections (content-types) et le composant du backend ;
  - tous leurs champs, avec type, taille, obligation, unicité, valeur par
    défaut et utilité ;
  - les relations entre collections ;
  - les champs automatiques (système ou générés par le code) ;
  - les incohérences constatées entre le schéma et le code.

Aucun fichier du projet n'a été modifié : ce document est le seul fichier créé.

================================================================================

L'analyse s'appuie sur quatre sources complémentaires :

AVERTISSEMENT IMPORTANT SUR backend/database/database.sql :
ce fichier est un export binaire pg_dump d'une base PostgreSQL nommée « ms »
(tables a_la_une, actu, contacts, d_info, visiteurs, users1, etc.). Il ne

================================================================================
2. CONVENTIONS DE LECTURE
================================================================================

• Type logique : type déclaré dans le schéma Strapi.
• Type physique : type de colonne réellement observé dans SQLite.
• Taille : taille physique observée. Strapi utilise varchar(255) par défaut
  pour les chaînes ; les champs « text » n'ont pas de taille déclarée.
• Obligatoire : « oui (app.) » signifie que Strapi refuse la création sans
  ce champ. IMPORTANT : SQLite ne porte PAS de contrainte NOT NULL sur ces
  colonnes (vérifié par PRAGMA) ; l'obligation est donc applicative.
• Unique : « oui (app.) » signifie que le schéma déclare unique. Aucun index
  UNIQUE n'a été observé en SQLite sur les champs métier (références,
  qr_token, cleUnicite) : l'unicité n'est garantie que par le contrôle
  applicatif (et par des vérifications manuelles dans les contrôleurs).
• Les liens manyToOne / oneToMany de Strapi 5 ne créent PAS de colonne de
  clé étrangère dans la table porteuse : ils sont stockés dans une TABLE DE
  LIAISON dédiée (une par relation). C'est un point essentiel pour le modèle
  conceptuel : par exemple `sorties.demande` n'existe pas comme colonne de
  `sorties`, mais dans la table `sorties_demande_lnk`.
• Les énumérations sont stockées en varchar(255) ; leurs valeurs sont
  contrôlées par l'application, pas par la base.
• Les dates métier (`date`) sont stockées au format AAAA-MM-JJ.
• Les horodatages (`datetime`) sont stockés au format ISO (date + heure).
• Les décimaux sont stockés en float (SQLite REAL) ; aucune précision n'est
  déclarée dans les schémas.
• Le fuseau métier utilisé par le code pour calculer « aujourd'hui » est
  Indian/Antananarivo (UTC+3), voir src/utils/horloge.js : les dates
  enregistrées sont des jours calendaires malgaches, pas des jours UTC.

Champs système présents dans TOUTES les tables de content-types (voir §17) :
id, document_id, created_at, updated_at, published_at, created_by_id,
updated_by_id, locale. Ils ne sont pas répétés dans chaque tableau de champs
pour rester lisible, mais ils existent physiquement partout.

18.2 Relations ABSENTES (données dénormalisées en texte)

  - affectations : direction, service_source, service_destinataire, materiel,
    materiel_reference, createur, createur_email, responsable_transfert,
    depositaire, chef_service_1, chef_service_2, signataires, dates de
    signature -> AUCUNE clé étrangère. Il est impossible de joindre une
    affectation à un service ou à un matériel par SQL.
  - mouvements.materiel : texte concaténé, pas de FK vers materials.
  - mouvements.utilisateur : texte, pas de FK vers up_users.
  - entrees : les 3 signataires et leurs dates sont du texte.
  - sorties : les 3 signataires, leurs dates, detenteur_nom, mandataire_nom
    sont du texte.
  - receptions_physiques.utilisateur : texte.
  - remises_detenteurs.direction / demandeur_nom : texte (le demandeur existe
    toutefois aussi en relation).
  - direction et services des utilisateurs : la relation existe, mais le code
    utilise aussi le préfixe texte de `department`.

18.3 Conséquence pour le mémoire

Le modèle conceptuel doit distinguer :
  (a) les relations normalisées (tables de liaison ci-dessus) ;
  (b) les relations « documentaires » volontairement figées en texte pour
      l'historique/audit (signataires, détenteurs, libellés de direction).
Les champs de (b) ne sont pas des clés étrangères et ne doivent pas être
présentés comme telles dans le dictionnaire.

20. CHAMPS AUTOMATIQUES ET CALCULES PAR LE SERVEUR
================================================================================

20.1 Champs automatiques du framework (toutes les tables)
  - id : clé primaire auto-incrémentée.
  - document_id : identifiant public généré par Strapi 5.
  - created_at / updated_at : horodatage système.
  - published_at : null si draftAndPublish=false.
  - created_by_id / updated_by_id : utilisateur de l'administration Strapi.
  - locale : non utilisé (i18n non configuré).

20.2 Champs générés par le code métier

  Références de dossier (générées si le client n'en fournit pas) :
    - demande.reference  : DEM-AAAA-NNN (service demande.js ; comptage des
      références existantes de l'année + 1).
    - entree.reference   : ENT-AAAA-NNN (contrôleur entree.js ; max des
      numéros existants + 1).
    - sortie.reference   : SOR-AAAA-NNN (utils/creationSortie.js).
    - affectation.reference : AFF-AAAA-NNN (contrôleur affectation.js).

  Identifiants et jetons :
    - entree.qr_token     : « ENT-<base36 horodatage>-<8 caractères aléatoires> ».
    - affectation.qr_token: « AFF-<base36 horodatage>-<8 caractères aléatoires> ».
    - notification_outboxes.cleUnicite : `<eventType>:<documentId>:<recipientId>`.

  Valeurs calculées :
    - entree_lignes.montant = quantite × valeur_unitaire (arrondi centime).
    - entrees.total = somme des montants des lignes.
    - sortie_lignes.montant = quantite × valeur_unitaire.
    - reception_lignes.quantite_reliquat = quantite_commandee - quantite_recue.
    - demandes.groupe = reference si le client ne le fournit pas.

  Compteurs et verrous :
    - receptions.version : 1 à la création, +1 à chaque mise à jour.
    - entrees.stock_impacte / sorties.stock_impacte : false à la création,
      true après l'impact stock (idempotence).
    - sorties.notifications_validee_envoyees : false puis true après émission.
    - sorties.remise_detenteur_cloturee : false puis true à la remise.
    - notification_outboxes.status/attempts/lastAttemptAt/lastError : gérés
      par le service de distribution (pending -> processing -> sent/failed).

  Valeurs posées côté serveur dans les contrôleurs :
    - demandes.demandeur = utilisateur connecté (jamais le corps de requête).
    - entrees.demandeur = utilisateur connecté.
    - entrees.affectation_depositaire = nom de l'utilisateur connecté si absent.
    - demandes.valide_par / date_validation = validateur et date de décision.
    - receptions.createdBy / updatedBy = utilisateur connecté (champ déclaré,
      voir la réserve du §23, point 6).
    - sorties.statut : en_preparation à la création, validee à la 3e
      signature, sortie_effectuee à la remise, annulee au rejet.
    - remises_detenteurs.date_enregistrement = horodatage ISO serveur.
    - sorties.remise_detenteur_date = date de remise recopiée.
    - mouvements : créés par les contrôleurs à chaque étape (traçabilité).
    - materials.quantite_stock : incrémenté à la validation d'une entrée,
      décrémenté atomiquement à la 3e signature d'une sortie.

20.3 Dates métier
  Les dates « du jour » sont calculées dans le fuseau Indian/Antananarivo
  (UTC+3) par src/utils/horloge.js, et stockées en AAAA-MM-JJ.


================================================================================
21. CYCLES DE STATUT OBSERVES
================================================================================

21.1 Demande (demandes.statut)
  Valeurs : brouillon, en_attente, en_cours, approuvee, rejetee, preparation,
  annulee, sortie_effectuee.
  Transitions ATTESTEES par le code lu :
    - création : brouillon ou en_attente ;
    - décision : en_attente -> approuvee ou en_attente -> rejetee ;
    - remise au détenteur : la demande liée passe à sortie_effectuee ;
    - demandeur : peut poser brouillon / en_attente / annulee.
  Les transitions vers en_cours et preparation ne sont PAS explicitement
  tracées dans les contrôleurs lus : à vérifier avant de les présenter comme
  un enchaînement certain.
  Contrôles : décision réservée au rôle depositaire ; statut de départ
  obligatoirement en_attente ; motif_rejet obligatoire en cas de rejet.

21.2 Entrée (entrees.statut)
  brouillon -> en_attente -> validee (après 3 signatures) ; rejetee possible.
  Les signatures sont des booléens indépendants : depositaire_signed,
  chef_service_1_signed, chef_service_2_signed. La 3e signature déclenche
  l'impact stock et le statut validee.
  (La valeur `verifiee` existe dans l'énumération mais son usage n'a pas été
  observé dans les contrôleurs lus : information non déterminée.)

21.3 Sortie (sorties.statut)
  en_preparation (création) -> validee (3e signature logistique, débit stock)
  -> sortie_effectuee (remise au détenteur) ; annulee (rejet).
  Signatures : magasinier -> depositaire -> logistique.

21.4 Réception (receptions.statut)
  en_cours -> partielle | complete, selon les reliquats cumulés ; annulee
  possible. La version est incrémentée lors du changement d'état.

21.5 Réception physique (receptions_physiques.statut)
  conforme (défaut) | anomalie.

21.6 Affectation (affectations.statut)
  en_attente -> validee après 4 signatures (responsable transfert,
  dépositaire, chef service 1, chef service 2).

21.7 Anomalie (anomalies.statut)
  ouverte -> en_cours -> resolue | rejetee. Journalisée dans journal-actions.

21.8 Notification outbox (notification_outboxes.status)
  pending -> processing -> sent ; failed après échec (retry par cron chaque
  minute, max 5 tentatives).

22. CONTRAINTES ET INTEGRITE
================================================================================

22.1 Contraintes réellement portées par SQLite
  - Clé primaire `id` sur toutes les tables.
  - Clés étrangères des tables de liaison vers les tables cibles (avec la
    particularité que les tables de liaison portent des FK vers les deux
    côtés).
  - Clés étrangères created_by_id / updated_by_id -> admin_users.id.
  - Contrainte UNIQUE sur les couples des tables de liaison.
  - Contraintes UNIQUE propres au plugin upload (upload_folders.path,
    upload_folders.path_id).

22.2 Contraintes déclarées mais NON portées par la base
  - `required: true` : aucune colonne métier n'est NOT NULL en SQLite.
  - `unique: true` sur reference / qr_token / cleUnicite : aucun index unique
    correspondant n'a été observé. L'unicité repose sur le code.
  - `min` / `max` (ex. ouverture_exercices.annee, quantite >= 1) : contrôles
    applicatifs uniquement.
  - Les énumérations : pas de CHECK en SQLite ; valeurs contrôlées par Strapi.

22.3 Règles applicatives structurantes
  - Un seul ordre de sortie par demande (contrôle 409).
  - Une seule remise au détenteur par sortie (verrou remise_detenteur_cloturee).
  - Débit de stock atomique et idempotent (stock_impacte + UPDATE conditionnel).
  - Réception possible seulement pour une sortie au statut validee (modèle
    reception) ou sortie_effectuee (modèle reception-physique).
  - Remise possible seulement pour une sortie sortie_effectuee avec une
    réception physique quantite_recue > 0.
  - Isolation par direction : un demandeur ne lit/crée que les objets de sa
    direction (contrôleurs).
  - Rôle Demandeur : écriture limitée aux demandes (roleGuard.js).
  - Idempotence des notifications (cleUnicite) et de la création de réception
    (clé idem_key — voir réserve §23).

23. INCOHERENCES ET POINTS A VERIFIER (constatés, non corrigés)
================================================================================

1) `reception` : le schéma déclare `numero` en integer, mais le contrôleur
   create exige `typeof body.numero === 'string'`. Une chaîne ne peut pas
   être stockée dans une colonne integer sans conversion ; le comportement
   réel dépend de Strapi. À trancher avant de documenter le type définitif.

2) `reception` : le contrôleur utilise une clé d'idempotence `idem_key`
   (filtre sur idem_key et écriture de idem_key). Ce champ N'EXISTE NI dans le
   schéma NI dans la table `receptions`. La création pourrait échouer ou
   l'idempotence ne pas être effective. À vérifier par un test d'exécution.

3) `reception` : le contrôleur écrit des mouvements avec les champs `date` et
   `createdBy`, alors que `mouvements` déclare `date_mouvement` et
   `utilisateur` (et n'a pas de champ date/createdBy). Incohérence de schéma.

4) `reception` : le contrôleur crée des entrées outbox avec les eventType
   `reception_complete` et `reception_partielle`, absents de l'énumération
   `eventType` (qui contient 6 autres valeurs). Selon le mode d'écriture,
   Strapi peut refuser ces valeurs.

5) `sortie_lignes` : le code envoie `designation`, champ absent du schéma et
   de la table.

6) `receptions.createdBy` / `updatedBy` : relations déclarées vers
   users-permissions.user, mais aucune table de liaison n'existe. Les colonnes
   physiques created_by_id / updated_by_id pointent vers admin_users. Le sens
   métier « créé par l'utilisateur » n'est donc pas garanti par la base.

7) `notification_outboxes` : doublons de colonnes (lastAttemptAt et
   last_attempt_at ; cleUnicite et cle_unicite) et colonnes historiques
   (sortie_document_id, demande_document_id) non utilisées par le code actuel.

8) Deux modèles de réception coexistent (`reception` et `reception-physique`),
   avec des statuts de sortie attendus différents (validee vs
   sortie_effectuee) et des règles de direction différentes (relation vs
   préfixe de department). Il faut choisir lequel décrire dans le mémoire, ou
   présenter les deux comme des versions successives.

9) `affectations` ne contient aucune clé étrangère et ne modifie pas le stock :
   c'est un registre documentaire, pas un mouvement de stock. À ne pas
   confondre avec `mouvements` dans le modèle conceptuel.

10) Unicité des références non garantie par la base. Les générateurs lisent le
    maximum existant puis écrivent : deux créations concurrentes peuvent
    produire la même référence (aucun verrou ni index unique observé).

11) `backend/database/database.sql` est un export PostgreSQL d'une autre base
    (« ms ») ; il ne décrit pas Compta. Ne pas l'utiliser comme source.

25. SYNTHESE POUR LE MEMOIRE

Entités principales et leur rôle :

  Utilisateur (up_users)       : compte métier, rôle, direction, département.
  Direction / Service / Employé: organigramme.

  Fournisseur                 : partenaire des entrées.

  Réception / Ligne            : contrôle à la livraison, reliquats, anomalies.
  Réception physique           : variante simplifiée de la réception.
  Remise au détenteur          : transfert final vers une personne physique.
  Affectation                  : transfert entre services (registre texte).
  Anomalie / Journal d'action  : traitement des écarts.
  Mouvement                    : journal de traçabilité transverse.
  Notification / Outbox        : notifications temps réel et file de reprise.
  Ouverture d'exercice         : stock initial pour la reddition.

  Direction 1-N Service 1-N Employé

  Catégorie 1-N Matériel

  Utilisateur 1-N Demande N-1 Direction / Service
  Demande 1-N Sortie 1-N Ligne de sortie N-1 Matériel
  Sortie 1-N Réception 1-N Ligne de réception N-1 Matériel
  Sortie 1-N Remise au détenteur 1-N Ligne de remise N-1 Ligne de sortie
  Réception 1-N Anomalie 1-N Journal d'action
  Entrée / Sortie / Demande 1-N Mouvement
  Sortie / Demande 1-N Notification outbox

  1) Un tableau « Tables et collections » (section 3).
  2) Un tableau par entité avec les colonnes : nom, type, taille,

  5) Une sous-section « limites et réserves » reprenant la section 23 : c'est
