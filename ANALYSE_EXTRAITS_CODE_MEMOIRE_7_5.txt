================================================================================
 INTRODUCTION
================================================================================

Le système étudié couvre le cycle de vie du matériel d'une organisation :
expression d'un besoin par un service, décision d'un responsable, préparation
et contrôle du matériel par le magasin, triple signature de l'ordre de sortie,
remise physique, réception par le dépositaire de la direction demandeuse, puis
affectation nominative au détenteur final. Il produit en outre un journal de
comptabilité matière (mouvements) et des états de reddition de compte.

L'architecture est de type « API d'abord » :

  - le backend est une application Strapi 5 (Node.js) exposant une API REST
    générée par content-type, complétée de contrôleurs métier écrits à la main
    pour les opérations sensibles (signature, validation, remise, réception,
    rapports) ;
  - la base de données est PostgreSQL, interrogeable directement via l'objet
    `trx` de Knex dans les transactions critiques (verrous conditionnels,
    décrément atomique du stock) ;
  - le frontend est une application React (TypeScript) qui consomme cette API
    par un module central `lib/api.ts` et n'effectue aucun calcul de stock.

Le fil conducteur de l'analyse est la séparation des responsabilités :

  1. le frontend ne décide jamais du stock, du statut ni du signataire : il
     envoie une intention (signer, remettre, réceptionner) et affiche la
     réponse du serveur ;
  2. le backend vérifie le rôle réel de l'utilisateur connecté (jamais un rôle
     transmis par le client), l'ordre des signatures, la disponibilité du
     stock, puis écrit dans une transaction unique ;
  3. le stock n'est débité qu'une seule fois, à la troisième signature de
     l'ordre de sortie ; les étapes suivantes (remise, réception, affectation)
     ne le touchent plus et ne produisent que des mouvements de traçabilité.

Les onze fonctionnalités analysées sont les suivantes :

   1. Authentification, rôles et contrôle des accès
   2. Gestion des utilisateurs, directions et services
   3. Gestion des matériels et des fournisseurs
   4. Entrées de matériel et impact sur le stock
   5. Expression et traitement des demandes de matériel
   6. Circuit de sortie : les trois signatures et le débit du stock
   7. Préparation des matériels et remise physique
   8. Réception par le dépositaire de direction
   9. Affectation du matériel au détenteur
  10. Retours, pertes et inventaire
  11. Journal des mouvements et reddition de compte

Pour chacune, le document présente : les fichiers concernés (A), des extraits
de code commentés avec leurs numéros de ligne (B), l'explication du
fonctionnement, des données et des règles de gestion (C), puis la capture
d'écran à produire pour l'illustration du mémoire (D).

```js
async function getRoleCode(strapi, userId) {
  try {
    const user = await strapi.db
      .query('plugin::users-permissions.user')
      .findOne({ where: { id: userId }, populate: ['role'] });
    if (!user || !user.role) return '';
    // Strapi users-permissions : le code du rôle est `type`
    // (`code` reste toléré pour compatibilité).
    const code = user.role.code || user.role.type || '';
    return code.toString().toLowerCase();
  } catch (e) {
    return '';
  }
}
```

```js
async function assertCanWrite(strapi, ctx, uid) {
  const userId = ctx.state && ctx.state.user ? ctx.state.user.id : null;
  if (!userId) {
    return; // non authentifie -> gere par l'authentification Strapi
  }

  const code = await getRoleCode(strapi, userId);
  if (!code || code !== DEMANDEUR_ROLE) return;

  if (uid !== DEMANDE_UID) {
    forbid(
      ctx,
      "Votre rôle (Demandeur) ne vous permet pas de modifier ou de supprimer ces données."
    );
    return;
  }
```

```js
function guardedCoreController(createCoreController, uid, customMethods = {}) {
  return createCoreController(uid, ({ strapi: app }) => ({
    async create(ctx) {
      await assertCanWrite(app, ctx, uid);
      if (ctx.status === 403) return ctx.body;
      return super.create(ctx);
    },
    async update(ctx) {
      await assertCanWrite(app, ctx, uid);
      if (ctx.status === 403) return ctx.body;
      return super.update(ctx);
    },
    async delete(ctx) {
      await assertCanWrite(app, ctx, uid);
      if (ctx.status === 403) return ctx.body;
      return super.delete(ctx);
    },
    ...customMethods,
  }));
}
```

```ts
export function mapStrapiUser(
  user: StrapiAuthUser | null | undefined
): User | null {
  if (!user) return null;
  const role = (user.role?.type || user.role?.code || "").toLowerCase();
  const isKnown =
    role === "admin" || (KNOWN_APP_ROLES as string[]).includes(role);
  if (!isKnown) return null;

  return {
    id: user.documentId || String(user.id),
    strapiId: user.id,
    name: user.username,
    email: user.email,
    role: role as User["role"],
    department: user.department || "",
    directionId: user.direction?.id?.toString() ?? undefined,
    directionName: user.direction?.nom_direction ?? undefined,
    permissions: ["equipment.view"],
    ...(role === "demandeur"
      ? { demandeurLevel: (user.department || "").includes(" - ") ? ("service" as const) : ("direction" as const) }
      : {}),
  };
}
```

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Établir une identité fiable avant toute opération, et faire en sorte que le
  rôle utilisé pour autoriser une action soit toujours celui enregistré en base,
  jamais une valeur envoyée par le navigateur.

Fonctionnement des instructions

  - `getRoleCode` (extrait 1.1) est la brique de base. Elle interroge la table
    des utilisateurs du plugin `users-permissions` avec `populate: ['role']`
    afin de charger la relation de rôle dans la même requête SQL, puis lit
    `user.role.code` et, à défaut, `user.role.type` — Strapi nommant le code du
    rôle `type` dans ses versions récentes. La valeur est convertie en
    minuscules pour rendre les comparaisons insensibles à la casse. En cas
    d'erreur (utilisateur supprimé, relation absente), la fonction renvoie une
    chaîne vide : aucun appelant ne peut alors considérer l'utilisateur comme
    autorisé, ce qui place le système en refus par défaut.

  - `assertCanWrite` (extrait 1.2) applique une règle métier simple : le profil
    « demandeur » ne peut écrire que sur la ressource `api::demande.demande`.
    La fonction sort immédiatement si l'appel n'est pas authentifié (le cas est
    traité en amont par la couche d'authentification de Strapi), puis compare
    le code de rôle à la constante `DEMANDEUR_ROLE`. Si l'utilisateur est
    demandeur et que la ressource visée n'est pas la demande, la fonction
    `forbid` positionne un statut HTTP 403 et un corps d'erreur normalisé
    (`error.status`, `error.name`, `error.message`).

  - `guardedCoreController` (extrait 1.3) est une fabrique : elle reçoit la
    fonction `createCoreController` de Strapi, l'identifiant du content-type et
    un objet de méthodes personnalisées. Elle renvoie un contrôleur dont les
    trois opérations d'écriture (`create`, `update`, `delete`) appellent
    d'abord `assertCanWrite`, testent `ctx.status === 403` et n'appellent
    l'implémentation standard (`super.create`, etc.) que si le contrôle est
    passé. Les méthodes métier supplémentaires sont fusionnées par
    `...customMethods`, ce qui permet à un module d'ajouter, par exemple, une
    route de signature tout en héritant du même contexte Strapi.

  - `APP_ROLES` (extrait 1.4) décrit les cinq profils métier : demandeur,
    dépositaire par service, magasinier, chef logistique, comptable. Chaque
    entrée porte un `type` (code technique, stocké en base), un `name`
    (libellé affiché) et une `description` qui documente les droits. Ce
    tableau est la source unique de vérité : les mêmes codes sont réutilisés
    par les contrôleurs métier (`SIGNATURE_ROLES` des modules `entree` et
    `sortie`).

  - `ensureAuthSetup` (extrait 1.5) rend le déploiement reproductible : pour
    chaque définition, elle cherche le rôle par son `type` et ne le crée que
    s'il est absent. Un redémarrage ne duplique donc pas les rôles et ne
    réécrit pas leurs libellés.

  - La route de session (extrait 1.6) répond à un problème concret de Strapi :
    le service de documents applique un « sanitizer » qui supprime la relation
    `role` des réponses utilisateur. Le contrôleur construit donc la réponse à
    la main (`return { data: { ... } }`) pour que le rôle, le département, la
    fonction et la direction soient réellement transmis. Elle renvoie 401 si
    aucun utilisateur n'est attaché au contexte de la requête.

  - Côté frontend (extrait 1.7), la connexion se fait en deux temps : appel de
    `strapiLogin(email, password)` qui renvoie un jeton et l'utilisateur brut,
    puis appel de `fetchSessionRole()` qui fournit la vue enrichie. Le jeton et
    l'utilisateur sont mémorisés (`setStrapiSession`), puis l'utilisateur est
    normalisé avant d'être remonté au composant parent (`onLogin`). Si
    l'authentification réussit mais que le rôle est inconnu, un message
    explicite est affiché et la connexion est refusée : on ne laisse jamais
    entrer un compte sans rôle applicatif.

  - `mapStrapiUser` (extrait 1.8) vérifie que le rôle appartient à la liste
    `KNOWN_APP_ROLES` (ou vaut `admin`) et renvoie `null` sinon. Elle construit
    l'objet `User` utilisé partout dans l'interface et dérive un
    `demandeurLevel` : si le libellé du département contient le séparateur
    « - », le demandeur est rattaché à un service, sinon à une direction.

Données manipulées
  Table `up_users` (plugin users-permissions) : `id`, `documentId`,
  `username`, `email`, `department`, `fonction` ; table `up_roles` : `id`,
  `type`, `name`, `description` ; table de liaison utilisateur-rôle. Côté
  frontend : objet `User` (identifiant, nom, courriel, rôle, département,
  direction, permissions).

Règles de gestion
  R1. Le rôle est toujours relu en base à partir de l'identifiant de session.
  R2. Un compte sans rôle applicatif connu ne peut pas se connecter.
  R3. Le profil « demandeur » n'a de droit d'écriture que sur ses demandes.
  R4. Toute réponse d'erreur d'autorisation est un HTTP 403 au format
      `{ error: { status, name, message } }`.
  R5. Les rôles sont créés de façon idempotente au démarrage : un déploiement
      successif ne crée pas de doublons.

Résultat attendu
  À la connexion, l'utilisateur obtient un jeton et un objet de session
  contenant son rôle métier ; toutes les opérations d'écriture ultérieures sont
  filtrées par ce rôle, côté serveur.

Limites constatées
  - Le contrôle d'accès en lecture n'est pas uniforme : `assertCanWrite` ne
    couvre que les écritures, et chaque module métier ajoute ses propres
    contrôles de lecture (par exemple `assertCanReadRapports` pour les
    rapports). Il n'existe pas de matrice centralisée « rôle × ressource ».
  - Le rôle `admin` applicatif est traité comme un rôle de secours dans
    plusieurs contrôleurs (`estAdmin`), ce qui contourne la séparation des
    tâches ; ce point doit être présenté comme un choix d'exploitation et non
    comme une règle métier.

```js
async function getDirectionIdsDuUtilisateur(strapi, user) {
  const departement = (user && user.department) || '';
  const separateur = departement.indexOf(' - ');
  const directionNom = separateur >= 0
    ? departement.slice(0, separateur).trim()
    : departement.trim();
  if (!directionNom) return [];

  const directions = await strapi.documents(DIRECTION_UID).findMany({
    filters: {
      $or: [
        { nom_direction: { $eqi: directionNom } },
        { abreviation: { $eqi: directionNom } },
      ],
    },
    fields: ['documentId'],
    limit: -1,
  });
  return (directions || []).map((d) => d.documentId);
}
```

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Décrire l'organisation (directions, services, employés) et expliquer comment
  le système rattache automatiquement un utilisateur à une direction, ce
  rattachement conditionnant l'accès aux sorties et aux réceptions.

Fonctionnement des instructions

  - Le modèle de direction (extrait 2.1) porte les informations d'identification
    (`nom_direction` obligatoire, `abreviation` utilisée dans les libellés
    courts, `directeur`, `directeur_email`, `localisation`) et une relation
    `oneToMany` vers `api::service.service` avec `mappedBy: "direction"` : la
    clé étrangère est portée par le service, la direction n'en conserve pas de
    copie.

  - `getDirectionIdsDuUtilisateur` (extrait 2.2) est la pièce centrale du
    rattachement. Le compte utilisateur ne possède pas de relation vers la
    table des directions : il possède un champ texte `department`, par exemple
    « Direction des Ressources Humaines - Service du personnel ». La fonction
    coupe ce libellé au premier séparateur « - » pour isoler le nom de la
    direction, puis recherche dans la table des directions une entrée dont
    `nom_direction` ou `abreviation` correspond, sans tenir compte de la casse
    (`$eqi`). Elle renvoie la liste des `documentId` trouvés — une liste, car
    rien n'interdit deux directions homonymes. Une liste vide signifie « aucune
    direction » : les contrôleurs qui l'utilisent refusent alors l'opération.

  - `fetchOrganisation` (extrait 2.3) illustre la lecture de l'organigramme par
    le frontend : un seul appel `GET /api/directions`, avec un `populate`
    imbriqué (`populate[services][populate][0]=employees`) pour charger en une
    requête les directions, leurs services et les employés de chaque service,
    triés par nom. Le résultat est ensuite projeté dans le type `OrgDirection`
    utilisé par les écrans d'organisation.

  - L'écran `Users.tsx` (extrait 2.4) montre, à l'inverse, une implémentation
    incomplète : la création affecte un identifiant calculé localement
    (`Date.now()`), la modification remplace l'objet dans le tableau d'état, la
    suppression filtre ce même tableau. Aucun appel HTTP n'est émis : ni
    `POST /api/users`, ni `PUT`, ni `DELETE`. Les comptes affichés proviennent
    d'un jeu de démonstration chargé dans `useState`. La conséquence est
    importante pour le mémoire : la création réelle d'un compte se fait
    aujourd'hui par l'administration de Strapi, pas par cette interface.

Données manipulées
  Tables `directions` (`nom_direction`, `abreviation`, `directeur`,
  `directeur_email`, `localisation`), `services` (`nom_service`,
  `responsable`, clé étrangère `direction`), `employees` (`im`, `nom`,
  `prenom`, `fonction`, clé étrangère `service`) et champ texte
  `up_users.department`.

Règles de gestion
  R1. Une direction est identifiée par son nom ou son abréviation, sans
      sensibilité à la casse.
  R2. Le rattachement d'un utilisateur à une direction est déduit du préfixe de
      son champ `department`, avant le séparateur « - ».
  R3. Un utilisateur sans direction résoluble ne peut ni réceptionner une
      sortie ni consulter les sorties de sa direction (voir sections 8 et 9).
  R4. La hiérarchie est direction → services → employés ; un service appartient
      à une seule direction.

Résultat attendu
  L'organigramme s'affiche avec ses trois niveaux, et chaque utilisateur
  connecté est rattaché à une direction, ce qui restreint automatiquement les
  listes de sorties et de réceptions qu'il peut traiter.

Limites constatées (à signaler dans le mémoire)
  - `Users.tsx` n'est pas connecté à l'API : création, modification et
    suppression de comptes ne sont pas persistées. La gestion des comptes se
    fait via le back-office Strapi.
  - Le rattachement à la direction repose sur une convention de chaîne de
    caractères (`department`), non sur une clé étrangère. Une faute de frappe
    dans le libellé suffit à priver l'utilisateur de ses droits sur les
    sorties de sa direction.
  - L'écran `Users.tsx` affiche des comptes de démonstration, y compris des
    mots de passe en clair dans son état initial ; ce point doit être corrigé
    avant toute mise en production et ne doit pas être illustré par une capture.

D. CAPTURE D'ÉCRAN RECOMMANDÉE

  employés) montrant au moins deux directions et leurs services. Une seconde
  capture peut montrer la fiche d'un utilisateur dans l'administration Strapi

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Disposer d'un référentiel unique d'articles (la fiche matériel) et d'un
  référentiel de fournisseurs, afin que chaque mouvement de stock puisse être
  rattaché à un article et à une origine identifiables.

Fonctionnement des instructions

  - La fiche matériel (extrait 3.1) isole trois champs décisifs.
    `quantite_stock` est un entier initialisé à 0 : c'est la seule grandeur que
    les circuits d'entrée et de sortie modifient. `valeur_unitaire` est un
    décimal qui sert au calcul des montants dans les lignes de mouvement et
    dans les états de reddition. `statut` est une énumération à cinq valeurs
    (`en_stock`, `distribue`, `maintenance`, `reforme`, `sortie`) : elle décrit
    la situation administrative de l'article, indépendamment de sa quantité.
    Deux articles différents ont deux fiches différentes : c'est cette fiche
    qui est visée par les clés étrangères des lignes d'entrée et de sortie.

  - Le contrôleur `material.js` est construit avec `guardedCoreController`
    (section 1, extrait 1.3). Les opérations d'écriture standard restent
    disponibles pour les rôles habilités, mais tout profil « demandeur » est
    arrêté par un 403 avant d'atteindre la base. Le frontend, lui, désactive
    explicitement les boutons d'ajout, de modification et de suppression
    (extrait 3.4) : le commentaire du code énonce la règle — « le stock évolue
    uniquement par le circuit d'entrée validé ». Une fiche matériel ne doit donc
    pas être créée « à la main » pour y inscrire une quantité : elle est créée
    par le circuit d'entrée, puis alimentée par la validation des entrées.

  - Le fournisseur (extrait 3.2) est un référentiel simple : nom obligatoire,
    coordonnées facultatives, et relation `oneToMany` vers les entrées. La
    relation est portée par l'entrée (`mappedBy: "fournisseur"`), ce qui permet
    de retrouver l'historique des livraisons d'un fournisseur sans dupliquer
    l'information.

  - `findOrCreateFournisseur` (extrait 3.3) résout un problème d'usage : à la
    saisie d'un bon de livraison, le magasinier tape un nom de fournisseur en
    texte libre. La fonction normalise d'abord la chaîne (suppression des
    espaces de bord et réduction des espaces multiples), puis tente une
    recherche exacte insensible à la casse (`$eqi`). Si elle échoue, elle
    charge tous les fournisseurs et compare une clé normalisée
    (`cleFournisseur`), ce qui rapproche « SOCIETE X » de « Société  X ». Ce
    n'est qu'en dernier recours qu'une fiche est créée. Ce comportement évite
    la prolifération de doublons tout en restant tolérant aux variations de
    saisie.

Données manipulées
  Table `materials` : `designation`, `nomenclature`, `categorie` (relation),
  `quantite_stock`, `valeur_unitaire`, `statut`, `observations`. Table
  `fournisseurs` : `nom`, `contact`, `email`, `telephone`, `adresse`. Table
  `entrees` : clé étrangère `fournisseur`.

Règles de gestion
  R1. Une quantité en stock est un entier positif ou nul, jamais négatif.
  R2. Le statut d'un article appartient à une liste fermée de cinq valeurs.
  R3. Le stock ne se modifie pas par édition directe de la fiche : il évolue
      par validation d'un circuit (entrée, sortie).
  R4. Un fournisseur est identifié par son nom, comparaison insensible à la
      casse et aux espaces multiples ; une fiche existante est réutilisée.
  R5. Un article peut exister en base avec une quantité nulle (fiche créée par
      une entrée, en attente de validation).

Résultat attendu
  L'écran « Matériels » présente, pour chaque article, la désignation, la
  nomenclature, la quantité en stock, la valeur unitaire et le statut, sans
  permettre de les modifier directement. Les fournisseurs saisis dans les
  entrées alimentent un référentiel unique.


Limites constatées
  - Les boutons d'ajout, modification, suppression et export de `Equipment.tsx`
    sont des fonctions vides : l'écran est en lecture seule. Toute création de
    fiche passe par le circuit d'entrée (section 4).
  - La multiplication de fiches matériel reste possible si deux désignations
    différentes sont saisies pour le même article : le rapprochement se fait
    sur la désignation exacte, sans référentiel de nomenclatures fermé.

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Enregistrer l'arrivée de matériel commandé, contrôler la conformité de la
  livraison, puis n'augmenter le stock qu'après réunion des trois signatures
  prévues — une seule fois.

Fonctionnement des instructions

  - `SIGNATURE_ROLES` (extrait 4.1) est la table de configuration du circuit.
    Chaque rôle est décrit par cinq propriétés : le drapeau booléen posé en
    base (`flag`), le champ date (`dateField`), le champ nom du signataire
    (`signerField`), le champ d'affectation (`affectationField`) et le rang
    (`order`). Les rangs 1, 2 et 3 sont portés respectivement par
    `chef_service_1` (magasinier), `chef_service_2` (logistique) et
    `depositaire`. Le commentaire de tête fixe la règle : la troisième
    signature déclenche la validation et l'impact stock.

  - `appliquerImpactStock` (extrait 4.2) matérialise l'unicité de l'impact.
    La première instruction est un retour immédiat si `stock_impacte` vaut déjà
    `true` : quelle que soit la répétition de l'appel, la quantité n'est pas
    ajoutée deux fois. Pour chaque ligne, la fiche matériel est récupérée
    (directement via la relation, ou par recherche sur la désignation si la
    relation est vide) ; les lignes sans fiche sont ignorées par `continue`,
    ce qui explique pourquoi la création de fiche à l'extrait 4.3 est
    indispensable. La nouvelle quantité additionne le stock courant et la
    quantité reçue, les deux valeurs étant converties en nombres avec repli sur
    0. Enfin, le drapeau `stock_impacte` est passé à `true` sur l'entrée.

  - L'extrait 4.3 montre la création des lignes d'entrée. Pour chaque ligne
    saisie, le code cherche d'abord une fiche existante par désignation
    exacte. Si aucune fiche n'existe, il en crée une avec la désignation
    nettoyée (`trim()`), la nomenclature, la valeur unitaire (si elle est
    numérique) et `quantite_stock: 0` — la quantité sera ajoutée plus tard par
    `appliquerImpactStock`. Le commentaire est explicite sur la raison d'être
    de ce bloc : sans fiche, la ligne resterait orpheline et son stock ne
    serait jamais impacté. Le `try/catch` qui suit journalise un avertissement
    sans interrompre la boucle : une ligne en échec n'empêche pas
    l'enregistrement des suivantes.

  - L'extrait 4.4 est le point de bascule du circuit. Après la pose de la
    signature courante, l'entrée est rechargée, puis le nombre de drapeaux à
    `true` est compté. Si ce nombre vaut 3, le statut passe à `validee` et
    `appliquerImpactStock` est appelée ; sinon le statut est `verifiee`. La
    validation et l'impact stock ne peuvent donc se produire qu'à la troisième
    signature, jamais avant.

  - Côté frontend, l'extrait 4.5 construit la charge utile de création. Le
    client n'envoie ni référence (générée par le serveur au format
    ENT-AAAA-NNN), ni statut, ni signature : il transmet la date, le bon de
    livraison, le fournisseur en texte libre, le responsable et les lignes. Le
    drapeau `exigerAffectations: false` correspond au flux « arrivée
    matériel » : l'écran ne connaît pas les trois signataires à l'avance, le
    serveur dérive l'affectation du dépositaire depuis la session et laisse les
    deux autres vides jusqu'à leurs signatures.

  - L'extrait 4.6 illustre le contrôle qualité obligatoire avant la première
    signature. Le composant vérifie que chaque article possède un état
    (`c.etat`) et qu'aucun n'est resté non contrôlé ; si c'est le cas, il
    affiche un message ciblé, marque l'article incomplet et interrompt le
    traitement (`return`) avant tout appel réseau. Les contrôles sont ensuite
    envoyés groupés avec la signature `chef_service_1` : l'état du matériel est
    donc enregistré dans le même appel que la signature.

Données manipulées
  En-tête d'entrée : `reference`, `date_entree`, `bon_livraison`,
  `date_bon_livraison`, `fournisseur`, `responsable`, `notes`, `statut`,
  `stock_impacte`, trois drapeaux `*_signed` et leurs dates et signataires.
  Lignes : `materiel`, `numero_ordre`, `designation`, `reference`, `espece`,
  `unite`, `quantite`, `valeur_unitaire`, `montant`, `nomenclature`,
  `piece_justificative`, `observations`, `etat`, `conforme`.

Règles de gestion
  R1. Une entrée suit l'ordre magasinier (1) → logistique (2) → dépositaire
      (3) ; une signature ne peut être ni devancée ni reposée.
  R2. Le statut reste `en_attente` ou `verifiee` tant que les trois signatures
      ne sont pas réunies ; il devient `validee` à la troisième.
  R3. Le stock est augmenté une seule fois, à la troisième signature, ligne par
      ligne, et le drapeau `stock_impacte` interdit toute seconde application.
  R4. Une ligne sans fiche matériel ne peut pas impacter le stock : une fiche
      est créée à la saisie avec une quantité nulle.
  R5. La référence de l'entrée est générée par le serveur ; le client ne peut
      pas l'imposer.
  R6. Chaque ligne doit être contrôlée (état renseigné) avant la certification
      du magasinier.

Résultat attendu
  Après saisie, l'entrée apparaît avec le statut correspondant à son
  avancement. À la troisième signature, le statut passe à « validée » et les
  quantités reçues sont ajoutées au stock des articles concernés.

Limites constatées
  - `appliquerImpactStock` n'est pas exécutée dans une transaction SQL : elle
    enchaîne des mises à jour unitaires. Une interruption entre deux lignes
    laisserait un stock partiellement incrémenté alors que `stock_impacte`
    n'aurait pas encore été posé. La protection contre le double impact est
    donc assurée, mais pas l'atomicité multi-lignes — différence avec le
    circuit de sortie, qui utilise `app.db.transaction`.
  - L'augmentation du stock est calculée en lecture puis écriture
    (`quantite_stock + quantite`) et non par un `increment` atomique : deux
    validations simultanées sur le même article peuvent se perdre.
  - `MaterialEntry.tsx` et `NewEntryPage.tsx` constituent deux chemins de saisie
    distincts ; le mémoire doit préciser lequel est présenté.

  affichée avec ses trois signatures et le statut « Validée ». Une capture de

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Permettre à un service d'exprimer un besoin chiffré sur des articles réels,
  faire décider ce besoin par le responsable habilité, puis transformer la
  décision en ordre de sortie sans aucune ressaisie.

Fonctionnement des instructions

  - `validerLignes` (extrait 5.1) est appelée à la création comme à la
    modification. Pour chaque ligne, elle convertit la quantité en nombre et
    exige un entier supérieur ou égal à 1 (`Number.isInteger`, `quantite < 1`).
    Elle refuse ensuite les articles dont le statut figure dans
    `MATERIEL_INDISPONIBLE` (articles en maintenance, réformés, etc.). Le
    contrôle décisif est le cumul : une table `cumulParMateriel` additionne les
    quantités de toutes les lignes visant le même article, ce qui empêche de
    contourner le contrôle de stock en éclatant une demande en plusieurs
    lignes. Si le cumul dépasse `quantite_stock`, la fonction renvoie un objet
    `{ erreur }` explicite, repris tel quel dans la réponse HTTP 400.

  - La création (extrait 5.2) applique le principe de la liste blanche : le
    serveur ne recopie pas le corps de la requête, il construit un objet `data`
    champ par champ. Le type est ramené à `entree` ou `sortie`, la priorité est
    validée contre la liste `PRIORITES`, le statut est calculé, le motif est
    nettoyé. Surtout, trois champs ne peuvent pas être falsifiés : `demandeur`
    reçoit l'utilisateur connecté (`user.documentId`), `direction` et `service`
    sont résolus à partir du compte (`resoudreOrganigramme`). Un utilisateur ne
    peut donc pas déposer une demande au nom d'un autre ni la rattacher à une
    autre direction.

  - L'approbation (extrait 5.3) est l'étape de décision du dépositaire. Le
    responsable peut ajuster la quantité de chaque ligne : la valeur proposée
    est contrôlée (entier ≥ 1, contrôle du cumul et du stock avec un HTTP 409
    en cas d'insuffisance). Les deux quantités sont conservées —
    `quantite_demandee` (valeur initiale) et `quantite` (valeur approuvée) — ce
    qui permet de tracer l'écart entre la demande et la décision. Le statut, le
    nom du validateur et la date sont posés par le serveur, jamais par le
    client.

  - `creerOrdre` (extrait 5.4) assure la continuité du circuit. Elle vérifie
    d'abord qu'aucun ordre de sortie n'est déjà rattaché à la demande
    (`filters: { demande: { documentId } }`) et renvoie un conflit 409 en
    citant la référence existante : une demande ne peut produire qu'un seul
    ordre. Le corps de l'ordre est ensuite entièrement prérempli depuis la
    base : date du jour, référence de la demande comme pièce justificative,
    direction et service de la demande, lignes avec les quantités approuvées,
    et lien `demande_id`. L'appel se termine par `preparerSortie`, la fonction
    partagée du circuit de sortie (section 6).

  - L'extrait 5.5 montre la contrepartie frontend : l'écran n'envoie que le
    type, la priorité, le statut, la date, le motif et les lignes identifiées
    par `documentId` du matériel. Il n'envoie ni demandeur, ni direction, ni
    service, ni référence — ces valeurs sont dérivées côté serveur.

Données manipulées
  Demande : `reference`, `type`, `statut` (brouillon, en_attente, approuvee,
  rejetee, sortie_effectuee), `priorite` (normal, urgent, critique),
  `date_demande`, `date_envoi`, `motif`, `designation_materiel`, `quantite`,
  `demandeur`, `direction`, `service`, `valide_par`, `date_validation`,
  `observation`. Lignes : `materiel`, `designation`, `quantite`,
  `quantite_demandee`, `motif`.

Règles de gestion
  R1. Une demande est créée par le demandeur connecté ; la possession et le
      rattachement organisationnel ne sont jamais transmis par le client.
  R2. Une quantité demandée est un entier ≥ 1.
  R3. Le cumul des lignes d'une même demande ne peut pas dépasser le stock
      disponible de l'article.
  R4. Un article indisponible (statut non distribuable) ne peut pas être
      demandé.
  R5. L'approbation peut réduire la quantité ; la quantité demandée initiale
      reste conservée pour la traçabilité.
  R6. Une demande approuvée ne peut donner qu'un seul ordre de sortie.
  R7. Les statuts de décision (`approuvee`, `rejetee`) ne sont pas modifiables
      par la route générique `update`.

Résultat attendu
  Le demandeur voit sa demande passer de « brouillon » ou « en attente » à
  « approuvée » ou « rejetée ». Une demande approuvée peut être transformée en
  ordre de sortie prérempli, sans nouvelle saisie.

Limites constatées
  - Le contrôle de stock à la création et à l'approbation est un contrôle
    indicatif : il ne réserve pas la quantité. Le stock peut être consommé par
    une autre sortie entre l'approbation et la validation logistique ; c'est
    cette dernière qui fait foi (section 6, extrait 6.3).
  - Le module `affectation` (transferts entre services, quatre signatures) est
    distinct de la demande et n'est pas mobilisé par ce circuit ; il ne doit
    pas être confondu avec l'affectation au détenteur (section 9).
  - `MyRequests.tsx` affiche des demandes : la création est bien persistée
    (appel `POST /api/demandes`), contrairement aux écrans de mouvements
    (section 11).

--- Extrait 6.2 — Contrôle du rôle, du statut et de l'ordre des signatures -----
Fichier : backend/src/api/sortie/controllers/sortie.js
Lignes  : 727-796

```js
  async sign(ctx) {
    const app = strapi;
    const { documentId } = ctx.params;
    const body = (ctx.request.body && ctx.request.body.data) || ctx.request.body || {};
    const roleKey = body.role;

    if (!SIGNATURE_ROLES[roleKey]) {
      return badRequest(ctx, "Rôle de signature inconnu (magasinier, depositaire, logistique).");
    }

    // --- Contrôle du rôle connecté ------------------------------------------
    const user = ctx.state && ctx.state.user;
    if (!user || !user.id) {
      return forbid(ctx, 'Authentification requise pour signer une sortie.', 401);
    }
    const code = (await getRoleCode(app, user.id)).toLowerCase();

    // Le Demandeur ne signe jamais (garde-fou redondant avec roleGuard.js).
    if (code === DEMANDEUR_ROLE) {
      return forbid(ctx, "Votre rôle (Demandeur) ne permet pas de signer une sortie.");
    }

    const config = SIGNATURE_ROLES[roleKey];
    const estAdmin = code === 'admin';
    if (!estAdmin && !config.roles.includes(code)) {
      return forbid(
        ctx,
        `Votre rôle ne permet pas d'apposer la signature « ${roleKey.replace(/_/g, ' ')} ».`
      );
    }

    const sortie = await loadSortie(app, documentId);
    if (!sortie) {
      ctx.status = 404;
      ctx.body = { error: { status: 404, name: 'NotFound', message: 'Sortie introuvable.' } };
      return ctx.body;
    }

    // --- Statut obligatoire : en_preparation ---------------------------------
    if (sortie.statut !== 'en_preparation') {
      return badRequest(
        ctx,
        `La signature n'est possible que pour une sortie « en_preparation » (statut actuel : ${sortie.statut || '—'}).`
      );
    }

    // --- Double signature interdite -------------------------------------------
    if (sortie[config.flag] === true) {
      return forbid(ctx, 'Cette signature a déjà été enregistrée et ne peut pas être modifiée.', 409);
    }

    // --- Ordre strict du workflow (TOUTES les signatures précédentes) --------
    // Pour la 3ᵉ signature, magasinier (1) ET dépositaire (2) doivent avoir
    // signé : le message nomme la première signature manquante.
    const precedents = Object.values(SIGNATURE_ROLES)
      .filter((c) => c.order < config.order)
      .sort((a, b) => a.order - b.order);
    for (const precedent of precedents) {
      if (sortie[precedent.flag] !== true) {
        return badRequest(
          ctx,
          `Signature manquante : la signature « ${precedent.signerField.replace('signataire_', '')} » doit être apposée avant celle-ci.`
        );
      }
    }

    // --- Étape 4 : la signature du chef logistique valide et débite le stock ----
    if (roleKey === 'logistique') {
      return await signerLogistique(app, ctx, sortie, documentId, user, body);
    }
```

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Sécuriser la sortie de matériel par trois signatures successives portées par
  trois fonctions distinctes, et faire en sorte que le stock ne soit débité
  qu'une seule fois, au moment précis où la troisième signature est posée.

Fonctionnement des instructions

  - `SIGNATURE_ROLES` (extrait 6.1) décrit les trois étapes. Contrairement à la
    table du module d'entrée, chaque entrée porte un tableau `roles` : le rôle
    autorisé à poser la signature est donc vérifié en base, et non déduit du
    libellé envoyé. L'ordre est fixé par `order` : 1 magasinier, 2 dépositaire,
    3 logistique. Les noms de champs (`magasinier_signed`,
    `depositaire_signed`, `logistique_signed`, et leurs `date_` / `signataire_`)
    sont les colonnes réellement écrites dans la table des sorties.

  - `sign` (extrait 6.2) est l'unique point d'entrée des trois signatures
    (`POST /api/sorties/:documentId/sign`). La méthode enchaîne des contrôles
    dans un ordre volontaire, du plus général au plus précis :
      1. le corps doit désigner un rôle connu, sinon 400 ;
      2. l'appel doit être authentifié, sinon 401 ;
      3. `getRoleCode` relit le rôle réel et le profil « demandeur » est refusé ;
      4. le rôle doit figurer dans `config.roles` (sauf `admin`, toléré comme
         rôle d'exploitation) ;
      5. la sortie doit exister, sinon 404 ;
      6. son statut doit être `en_preparation` : une sortie validée ou déjà
         remise ne peut plus être signée ;
      7. la signature visée ne doit pas déjà être posée (409), ce qui rend le
         double clic inoffensif ;
      8. toutes les signatures de rang inférieur doivent être présentes, sinon
         400 avec le nom de la signature manquante.
    Si ces huit contrôles passent et que le rôle est `logistique`, la méthode
    délègue immédiatement à `signerLogistique` : c'est la seule branche qui
    touche au stock.

  - L'extrait 6.3 détaille la signature du magasinier. Les `controles` sont
    obligatoires : un élément `{ ligne, etat, observations? }` par ligne. Le
    code construit une table `parLigne` indexée par `documentId` de ligne, puis
    parcourt les lignes de la sortie pour vérifier que chacune possède un
    contrôle dont l'état appartient à `ETATS_VALIDES` (`neuf`, `bon`, `moyen`,
    `defaillant`). Les lignes non conformes sont accumulées dans `manquants` et
    l'ensemble de la requête est refusé si la liste n'est pas vide. Un second
    garde-fou, juste après, vérifie qu'aucun contrôle ne référence une ligne
    d'une autre sortie. Les états sont ensuite écrits sur les lignes avant la
    pose de la signature, de sorte qu'aucun état intermédiaire incohérent ne
    subsiste.

  - L'extrait 6.4 est le cœur transactionnel. `app.db.transaction` ouvre une
    transaction Knex et fournit `trx`. Trois étapes s'y succèdent :
      a) lecture de toutes les pénuries avant toute écriture : chaque stock est
         lu, comparé à la quantité demandée, et les insuffisances sont
         collectées pour être renvoyées en une seule fois (HTTP 409), ce qui
         évite de découvrir la seconde pénurie après avoir déjà débité la
         première ligne ;
      b) verrou anti-double exécution : la mise à jour n'est appliquée que si
         `stock_impacte` vaut `false` et renvoie le nombre de lignes modifiées.
         Si ce nombre est nul, la sortie a déjà été validée : le code lève une
         `ErreurTransaction` 409 qui provoque le rollback ;
      c) décrémentations atomiques, ligne par ligne, avec un `where
         quantite_stock >= quantite` dans la clause de mise à jour. Le
         décrément n'est donc appliqué que si le stock est suffisant au moment
         exact de l'écriture ; dans le cas contraire, aucun enregistrement
         n'est modifié (`!nbDecrement`) et une erreur 409 est levée. Les lignes
         sont triées par `documentId` de matériel afin que deux sorties
         concurrentes verrouillent les fiches dans le même ordre et ne se
         bloquent pas mutuellement.

  - L'extrait 6.5 termine la transaction : pose de `logistique_signed`, du
    signataire et de la date ISO, passage de `stock_impacte` à `true` et du
    statut à `validee`, puis création d'un mouvement par ligne. Ces créations
    sont volontairement dépourvues de `try/catch` : une erreur de traçage
    annule toute la validation, ce qui garantit qu'une sortie validée possède
    toujours sa trace comptable.

  - `signerSortie` (extrait 6.6) est le seul appel utilisé par les trois
    écrans : le paramètre `role` distingue l'étape, `controles` n'est renseigné
    que pour le magasinier, `numeros_logistiques` que pour le chef logistique.
    Le délai est porté à 30 secondes car la requête exécute une transaction
    serveur. L'extrait 6.7 montre l'appel effectif à l'étape 3, avec
    `role: "logistique"`, et rappelle un piège corrigé : l'identifiant attendu
    est `sortie.id` (qui contient le `documentId` Strapi), faute de quoi l'URL
    devient `/api/sorties/undefined/sign`.

Données manipulées
  Sortie : `reference`, `date_sortie`, `statut`, `direction`, `service`,
  `demande`, `beneficiaire`, `responsable`, `justificatif`, `observations`,
  `magasinier_signed` / `depositaire_signed` / `logistique_signed`, leurs dates
  et signataires, `stock_impacte`, `date_remise`, `mandataire_nom`,
  `detenteur_nom`, `detenteur_fonction`, `remise_detenteur_cloturee`.
  Lignes : `materiel`, `designation`, `quantite`, `valeur_unitaire`, `montant`,
  `etat`, `observations`, `numero_logistique`.

Règles de gestion
  R1. Trois signatures dans un ordre strict : magasinier, dépositaire
      comptable, chef logistique. Aucune ne peut être devancée.
  R2. Une signature déjà posée ne peut être ni reposée ni modifiée (409).
  R3. La signature n'est possible que sur une sortie au statut
      `en_preparation`.
  R4. La signature du magasinier exige un contrôle d'état pour chaque ligne.
  R5. La troisième signature valide la sortie (`validee`) et débite le stock
      central, dans la même transaction.
  R6. Le débit est protégé par le verrou `stock_impacte` : une seule
      décrémentation possible, même en cas de requêtes simultanées.
  R7. Si un article est insuffisant, aucune ligne n'est débitée : la
      transaction est annulée et la liste complète des pénuries est renvoyée.
  R8. Aucun mouvement de traçage ne peut être omis : un échec de création
      annule la validation.

Résultat attendu
  La sortie passe de `en_preparation` à `validee` à la troisième signature, les
  quantités sorties sont retirées du stock, et le journal enregistre un
  mouvement « Sortie validée, stock débité » par ligne ainsi qu'un mouvement de
  signature.

Limites et points de vigilance
  - Le débit du stock a lieu à la troisième signature, c'est-à-dire avant la
    remise physique (section 7). Entre la validation et la remise, le stock
    affiché est donc inférieur au stock physiquement présent au magasin. Ce
    décalage est inhérent au circuit et doit être expliqué dans le mémoire.
  - La première signature (magasinier) est un contrôle de l'état du matériel
    effectué en amont de la validation. La règle « le magasinier prépare les
    matériels après validation » n'a pas d'étape dédiée dans le code : la
    sortie physique du magasin se confond avec la remise (section 7).
  - Le rôle `admin` applicatif contourne la vérification `config.roles` : il
    peut poser n'importe laquelle des trois signatures. La séparation des
    tâches n'est donc pas garantie pour ce profil.
  - `sign` accepte `numeros_logistiques` pour l'étape 3 ; ces numéros sont
    enregistrés tels quels, sans contrôle de format.

D. CAPTURE D'ÉCRAN RECOMMANDÉE
--------------------------------------------------------------------------------
  Trois captures successives du même ordre de sortie : (1) écran de préparation

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Distinguer deux moments que l'usage confond souvent : la préparation
  contrôlée du matériel (vérifier que l'article existe, qu'il est en état et en
  quantité suffisante) et la remise physique, qui constate la sortie du
  magasin et fait passer l'ordre au statut `sortie_effectuee`.

Fonctionnement des instructions

    conditions sont vérifiées avant tout appel réseau : toutes les lignes ont un
    état (`controle.etat` non vide), toutes les cases de vérification de
    présence sont cochées (`verifiees[controle.ligne] === true`), et toute ligne
    déclarée « défaillant » porte une remarque. Chaque échec produit un message
    distinct et un `return` immédiat : aucune requête partielle n'est envoyée.
    L'appel `signerSortie(sortie.id, "magasinier", controles)` transmet les
    contrôles ; la case à cocher, qui n'est qu'une aide d'écran, reste hors du
    payload. Les erreurs 403 et 409 sont traduites en messages métier.

  - Côté serveur, cette première signature écrit l'état de chaque ligne puis
    pose `magasinier_signed` (extrait 6.3 et lignes 883-893 du contrôleur). Le
    statut de la sortie reste `en_preparation` : la préparation ne valide rien
    et ne touche pas au stock.

  - `remise` (extraits 7.2 à 7.4) est une méthode distincte, appelée par
    `POST /api/sorties/:documentId/remise`. Elle vérifie d'abord que la remise
    n'est pas déjà enregistrée (409), puis que le statut est exactement
    `validee` : une sortie encore en préparation ne peut donc pas être remise.
    Le commentaire du code précise que le détenteur (nom et fonction) est
    optionnel à cette étape, car il sera identifié plus tard, lors de
    l'affectation (section 9).

  - L'écriture de la remise (extrait 7.3) ouvre une transaction. L'objet
    `donneesRemise` n'est construit qu'avec la date, et n'ajoute le détenteur ou
    le mandataire que s'ils sont renseignés : un champ vide ne provoque aucune
    écriture, ce qui évite d'écraser une valeur existante par une chaîne vide.

  - Dans la même transaction (extrait 7.4), un mouvement « Remise au
    détenteur » est créé, avec la date de remise, le signataire, la liste des
    désignations et la quantité totale, puis le statut de la sortie passe à
    `sortie_effectuee`. Aucune ligne de cet extrait ne modifie
    `quantite_stock` : la remise ne débite rien, le débit a eu lieu à la
    troisième signature.

  - `erreurDeSaisie` (extrait 7.5) regroupe les règles de forme de l'écran de
    remise : format de date `AAAA-MM-JJ`, date non postérieure à aujourd'hui,
    confirmation explicite que le matériel remis correspond à la liste. Le
    calcul est mémorisé par `useMemo` et rejoue dès qu'une des trois valeurs
    change.

  - L'extrait 7.6 montre le garde anti-double envoi (`envoiEnCours.current`, une
    référence et non un état, donc immédiatement à jour) et la construction du
    payload limité au mandataire et à la date. L'extrait 7.7 documente ce
    contrat : l'interface `PayloadRemise` ne comporte que deux champs, et le
    commentaire rappelle explicitement que le stock n'est pas touché par cet
    appel. Le délai de 30 secondes est nécessaire car la remise s'exécute dans
    une transaction.

Données manipulées
  Sortie : `date_remise`, `mandataire_nom`, `detenteur_nom`,
  `detenteur_fonction`, `statut` (`validee` → `sortie_effectuee`), champs de
  signature 1. Lignes : `etat`, `observations`. Mouvement : `reference`,
  `type`, `date_mouvement`, `utilisateur`, `action`, `materiel`, `quantite`,
  `statut`, `sortie`, `observations`.

Règles de gestion
  R1. La préparation exige un état pour chaque ligne et la confirmation de
      présence ; une ligne défaillante doit être motivée.
  R2. La préparation ne modifie pas le statut de la sortie et ne touche pas au
      stock.
  R3. La remise physique n'est possible que sur une sortie validée.
  R4. Une remise ne peut être enregistrée qu'une seule fois (409 ensuite).
  R5. La remise ne débite pas le stock : elle enregistre qui a reçu, quand, et
      éventuellement par quel mandataire.
  R6. La date de remise ne peut pas être future.
  R7. Le détenteur n'est pas obligatoirement connu à la remise ; il le sera à
      l'affectation, après réception.

Résultat attendu
  L'ordre passe à `sortie_effectuee`, le journal enregistre une remise, et le
  matériel est considéré comme sorti du magasin — sans aucune nouvelle
  modification du stock.

Limites et points de vigilance
  - La règle métier « le magasinier prépare les matériels après validation »
      n'est pas celle qu'implémente le code : la préparation-contrôle est la
      première signature, donc antérieure à la validation ; seule la remise
      physique intervient après la validation. Le mémoire doit présenter cette
      séquence réelle, ou signaler l'écart comme une évolution à prévoir.
  - Les deux étapes sont nommées de façon proche (« préparation » pour la
    signature 1, « remise » pour la sortie physique) ; il convient de les
    distinguer explicitement dans le texte et dans les captures.
  - Aucun contrôle ne vérifie que la personne qui reçoit physiquement le
    matériel est bien celle enregistrée : la remise constate, elle n'authentifie
    pas le récepteur.

D. CAPTURE D'ÉCRAN RECOMMANDÉE

  confirmation) et l'ordre affiché au statut « Sortie effectuée ». La fiche du

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif
  Permettre au dépositaire de la direction demandeuse de constater l'arrivée
  effective du matériel, d'enregistrer les quantités réellement reçues et de
  signaler une anomalie (manquant, endommagé, non conforme), avant toute
  affectation nominative.

Fonctionnement des instructions

  - Le modèle (extrait 8.1) impose une relation `sortie` obligatoire : une
    réception ne peut exister sans ordre de sortie. `quantite_prevue` et
    `quantite_recue` sont deux entiers obligatoires, ce qui permet de comparer
    l'attendu et le reçu. `statut` est une énumération à deux valeurs
    (`conforme` par défaut, `anomalie`) et `type_anomalie` en précise la nature
    (`manquant`, `endommage`, `incorrect`). `utilisateur` est un texte libre
    identifiant le déclarant.

  - `create` (extrait 8.2) vérifie quatre conditions avant d'écrire :
      1. la requête est authentifiée ;
      2. l'utilisateur possède le rôle « demandeur » — c'est le profil du
         dépositaire de direction, et le message d'erreur le dit explicitement ;
      3. la sortie référencée existe et son statut est `sortie_effectuee`,
         c'est-à-dire que la remise physique a déjà été enregistrée (section 7) ;
      4. la direction de la sortie fait partie des directions de l'utilisateur,
         résolues par `getDirectionIds` à partir de son champ `department`.
    Ces contrôles garantissent qu'un dépositaire ne peut pas réceptionner la
    sortie d'une autre direction, ni réceptionner un matériel qui n'a pas
    encore quitté le magasin.

  - La conversion de `sortieId` en `sortie` (lignes 134-137) est une
    adaptation au schéma Strapi : le client envoie une chaîne, la relation
    attend un identifiant de document ; le champ temporaire est supprimé du
    corps de la requête avant l'appel à `super.create`. Sans cette conversion,
    la relation serait refusée par le service de documents.

  - Le module `reception` (extrait 8.3) implémente une variante plus complète :
    chaque ligne de réception enregistre la quantité commandée, la quantité
    reçue et le reliquat (`quantite_commandee - quantite_recue`), avec une
    règle R6 qui interdit de recevoir plus que commandé. Le statut de l'en-tête
    est recalculé par `determinerStatutReception` en `en_cours`, `partielle` ou
    `complete` selon les reliquats cumulés. Ce module permet donc les
    réceptions partielles en plusieurs livraisons.

  - L'écran (extrait 8.4) construit la charge utile : identifiant de la sortie,
    date ISO, statut déduit de la case « déclaration d'anomalie », quantités
    prévue et reçue, utilisateur, et — uniquement si une anomalie est déclarée
    — le type et la description. Les deux champs d'anomalie sont ajoutés par
    spread conditionnel, donc absents du payload lorsqu'il n'y a pas d'anomalie.

Données manipulées
  Réception physique : `sortie`, `date_reception`, `statut`, `type_anomalie`,
  `description_anomalie`, `quantite_prevue`, `quantite_recue`, `utilisateur`.
  Réception (variante) : `numero`, `date_reception`, `statut`, `utilisateur`,
  `observations` ; lignes : `sortie_ligne`, `materiel`, `quantite_commandee`,
  `quantite_recue`, `quantite_reliquat`, `etat`, `observations`.

Règles de gestion
  R1. Seul un utilisateur de rôle « demandeur » (dépositaire de direction) peut
      enregistrer une réception.
  R2. La sortie doit être au statut `sortie_effectuee` : on ne réceptionne que
      ce qui a été physiquement remis.
  R3. La sortie doit appartenir à la direction de l'utilisateur.
  R4. Une réception est soit conforme, soit en anomalie ; l'anomalie est
      typée (manquant, endommagé, incorrect) et décrite.
  R5. La quantité reçue ne peut pas dépasser la quantité commandée (règle R6 du
      module `reception`).
  R6. Le reliquat est la différence entre quantité commandée et quantité reçue ;
      il détermine le caractère partiel ou complet de la réception.

Résultat attendu
  La réception est enregistrée et rattachée à l'ordre de sortie. Si elle est
  conforme, l'affectation au détenteur devient possible (section 9). Si elle
  est en anomalie, l'anomalie est historisée avec son type et sa description.

Limites et points de vigilance (important pour le mémoire)
  - Deux circuits de réception coexistent dans le dépôt. L'interface
    n'utilise que `reception-physique` (`/api/receptions-physiques`, appelé par
    `lib/api.ts` lignes 1800, 1811 et 1841). Le module `reception`, avec ses
    lignes et ses reliquats, n'est appelé par aucun écran du frontend : il
    constitue une implémentation disponible côté API mais non exposée. Le
    mémoire doit présenter le circuit réellement utilisé et signaler l'autre
    comme une évolution possible.
  - Le circuit `reception-physique` enregistre une quantité globale par
    réception, non un détail par ligne : il ne gère donc pas nativement les
    réceptions partielles article par article, contrairement au module
    `reception`.
  - Une réception en anomalie n'empêche pas techniquement l'affectation au
    détenteur : c'est la présence d'au moins une réception avec une quantité
    reçue positive qui est exigée (section 9). Le traitement de l'anomalie
    (remplacement, régularisation) n'est pas implémenté.

Objectif
  Nommer, article par article, la personne qui devient responsable du matériel
  au sein de la direction, une fois la réception confirmée. Cette étape clôt le
  circuit : après elle, le matériel n'est plus « sorti du magasin », il est
  « affecté à un détenteur ».

Fonctionnement des instructions

  - L'extrait 9.1 enchaîne trois conditions. La sortie doit d'abord être au
    statut `sortie_effectuee`, c'est-à-dire avoir été physiquement remise par le
    magasin. Ensuite, `receptionConfirmee` doit renvoyer au moins une réception :
    la fonction ne retient que les réceptions dont la quantité reçue est
    strictement positive, ce qui traduit la règle métier « pas d'affectation
    sans confirmation de réception ». Enfin, la sortie ne doit pas avoir déjà
    été clôturée (`remise_detenteur_cloturee`), ce qui renvoie un 409 en cas de
    seconde tentative.

  - L'extrait 9.2 impose la couverture intégrale : le nombre de lignes vues
    dans la demande d'affectation doit être égal au nombre de lignes de la
    sortie. On ne peut donc pas affecter une partie du matériel seulement ; le
    message d'erreur indique le décompte (`x/y couvertes`), ce qui aide
    l'utilisateur à identifier la ligne oubliée.

  - L'extrait 9.3 est le verrou d'unicité, exécuté dans la transaction. La
    colonne `remise_detenteur_cloturee` ayant été ajoutée après la création de
    certaines lignes, elle peut valoir `NULL` : le code effectue donc deux
    mises à jour conditionnelles successives (`NULL -> true`, puis
    `false -> true`). Si aucune des deux ne modifie de ligne, la remise est
    déjà enregistrée et une `ErreurTransaction` 409 provoque le rollback. Ce
    mécanisme rend le double clic et les envois concurrents inoffensifs, sans
    dépendre d'un verrou applicatif.

  - L'extrait 9.4 écrit une ligne d'affectation par matériel, avec
    `detenteur_nom` et `detenteur_fonction` en clair, puis met à jour la date de
    remise au détenteur sur la sortie. Le commentaire précédant la création du
    mouvement est explicite : aucune déduction de stock n'a lieu ici, car le
    débit a été effectué à la validation logistique. L'affectation ne produit
    donc qu'un mouvement de traçabilité.

  - Côté écran (extrait 9.5), la validation exige un nom et une fonction pour
    chaque ligne ainsi qu'une date de remise non future. Le payload (extrait
    9.6) reprend exactement ces valeurs, ligne par ligne, avec le booléen
    `attestation: true` qui matérialise l'engagement du dépositaire.

  - Point capital pour la règle métier : le détenteur n'est pas un compte
    utilisateur. `detenteur_nom` et `detenteur_fonction` sont des champs texte
    écrits tels quels (extrait 9.4) ; aucune relation vers la table des
    utilisateurs n'est créée. Une personne peut donc détenir du matériel sans
    jamais se connecter à l'application.

Données manipulées
  Remise au détenteur : `sortie`, `date_remise`, `demandeur_nom`,
  `attestation`, `date_enregistrement`. Lignes : `sortie_ligne`,
  `designation`, `quantite`, `detenteur_nom`, `detenteur_fonction`,
  `observation`. Sortie : `remise_detenteur_date`,
  `remise_detenteur_cloturee`.

Règles de gestion
  R1. L'affectation n'est possible qu'après réception physique confirmée
      (quantité reçue > 0).
  R2. La sortie doit être au statut `sortie_effectuee`.
  R3. Toutes les lignes du dossier doivent être affectées, chacune une seule
      fois.
  R4. Chaque ligne porte un nom et une fonction de détenteur.
  R5. Une seule affectation par dossier : le verrou transactionnel l'impose.
  R6. L'affectation ne modifie pas le stock.
  R7. Le détenteur est identifié par son nom et sa fonction, sans lien avec un
      compte utilisateur.

Résultat attendu
  Le dossier est clôturé côté direction : chaque matériel est rattaché à un
  détenteur nommé, la date d'affectation est enregistrée et un mouvement
  « Remise du matériel au détenteur » est ajouté au journal.

Limites et constatées
  - L'affectation est globale au dossier : aucune affectation partielle ou
    progressive n'est possible, alors que le matériel peut être distribué à
    plusieurs personnes à des dates différentes.
  - Le contrôle de la quantité affectée par ligne n'est pas vérifié ici contre
    la quantité réellement reçue : la couverture est vérifiée en nombre de
    lignes, non en quantités.
  - Une réception déclarée en anomalie avec une quantité reçue positive
    n'empêche pas l'affectation ; le traitement de l'anomalie reste manuel.
  - Le module `affectation` présent dans le dépôt est un circuit distinct
    (transferts entre services, quatre signatures). Il ne doit pas être
    présenté comme l'affectation au détenteur.

D. CAPTURE D'ÉCRAN RECOMMANDÉE
--------------------------------------------------------------------------------
  Écran d'affectation d'un dossier : tableau des lignes avec désignation,
  quantité, champ « détenteur » et champ « fonction », date de remise, case
  d'attestation. Puis la fiche du dossier clôturé montrant les détenteurs
  nommés et le mouvement correspondant dans le journal.

```js
function calculerInventaire({ annee, entrees, sorties, materiaux = [], ouvertures = [] }) {
  const entreesAnnee = lignesDeLAnnee(entrees, annee, 'entree');
  const sortiesAnnee = lignesDeLAnnee(sorties, annee, 'sortie');

  const parMateriel = new Map();

  function assurer(materielId, designation, nomenclature, valeurUnitaire, unite) {
    if (!parMateriel.has(materielId)) {
      parMateriel.set(materielId, {
        materielId,
        designation: designation || '—',
        nomenclature: nomenclature || '—',
        valeurUnitaire: Number(valeurUnitaire) || 0,
        unite: unite || 'N',
        entreesQ: 0,
        sortiesQ: 0,
      });
    }
    return parMateriel.get(materielId);
  }

  // Matériaux référencés dans la base (même sans mouvement, ils existent)
  for (const m of materiaux) {
    assurer(m.documentId || m.id, m.designation, m.nomenclature, m.valeur_unitaire, m.unite);
  }
  for (const l of entreesAnnee) {
    const m = assurer(l.materielId, l.designation, l.nomenclature, l.valeurUnitaire, null);
    m.entreesQ += l.quantite;
  }
  for (const l of sortiesAnnee) {
    const m = assurer(l.materielId, l.designation, l.nomenclature, l.valeurUnitaire, null);
    m.sortiesQ += l.quantite;
  }
```

C. EXPLICATION
--------------------------------------------------------------------------------

Objectif annoncé
  Clore le cycle de vie du matériel : enregistrer les retours, constater les
  pertes et produire l'inventaire annuel.

État réel de l'implémentation (à présenter tel quel dans le mémoire)

  1. INVENTAIRE — partiellement implémenté, sous forme d'état comptable.
     L'inventaire existe comme état de reddition : `GET /api/rapports/inventaire`
     (extrait 10.1) calcule, pour une année, les quantités entrées et sorties
     par article et en déduit le reste. `calculerInventaire` (extrait 10.2)
     construit une table `parMateriel` initialisée avec tous les articles
     référencés en base (même sans mouvement), puis ajoute les quantités des
     lignes d'entrée et de sortie de l'année. L'extrait 10.3 montre le calcul du
     reste : `resteQ = existantQ + entreesQ - sortiesQ`, avec `existantQ`
     volontairement fixé à 0 et commenté « stock physique initial par article
     non historisé ». La valorisation de l'existant est répartie par
     nomenclature au prorata des entrées.
     Ce qui n'existe pas : aucune campagne d'inventaire physique n'est
     implémentée. Il n'y a ni saisie de quantités comptées, ni rapprochement
     automatique entre stock théorique et stock constaté, ni clôture
     d'inventaire — alors que la description du rôle de dépositaire dans
     `ROLES_CONFIG` mentionne « clôture l'inventaire annuel ». L'écran
     correspondant n'est pas accessible : la clé `inventaire` est déclarée dans
     `ROLES_CONFIG` mais absente de `navItems` (`SimpleSidebar.tsx`).

  2. PERTES — non implémenté.
     La page `pertes` est déclarée dans `ROLES_CONFIG` (lignes 26, 36 et 56)
     pour les rôles dépositaire, magasinier et comptable, mais aucune entrée de
     navigation ne la référence et aucun module d'API ne traite une déclaration
     de perte. Il n'existe donc ni formulaire, ni statut, ni mouvement de type
     « perte ». Le mémoire doit indiquer cette fonctionnalité comme prévue mais
     non réalisée.

  3. RETOURS — non implémenté.
     La recherche des termes « restitution », « retour de matériel » et
     « retourner le matériel » dans l'ensemble du frontend ne renvoie aucun
     résultat ; aucun module backend ne traite un retour de matériel au magasin,
     aucune route, aucun statut, aucun mouvement inverse. Le circuit est
     strictement unidirectionnel : entrée → sortie → réception → affectation.

Fonctionnement des instructions (partie implémentée)

  - Le contrôleur `inventaire` (lignes 196-209) vérifie d'abord l'autorisation
    de lecture (`assertCanReadRapports`), lit et valide l'année, puis charge en
    bloc les lignes d'entrée, de sortie, les articles et les ouvertures avant
    d'appeler le service de calcul. Le calcul est donc séparé de l'accès aux
    données, ce qui le rend testable et réutilisable par les autres états.
  - `RedditionSection` (extrait 10.4) charge l'état correspondant à l'onglet
    actif. Pour le grand-livre, elle s'appuie sur l'inventaire pour choisir un
    article par défaut (le premier de la première nomenclature) lorsqu'aucun
    n'est sélectionné. Les appels sont centralisés dans `lib/reddition.ts`, qui
    renvoie `null` en cas d'échec plutôt que de propager une exception
    (lignes 149-156), et l'écran affiche alors un message d'erreur.
  - L'accès à la section est restreint côté interface aux rôles `depositaire` et
    `comptable` (ligne 133 : `if (!peutVoir) return null`), en plus du contrôle
    serveur.

Données manipulées
  Lignes d'entrée et de sortie de l'année (matériel, désignation, nomenclature,
  valeur unitaire, quantité, date), table des matériels, ouvertures annuelles
  par nomenclature. Résultat : par article, quantités existant / entrées /
  sorties / reste et valeurs correspondantes, regroupés par nomenclature.

Règles de gestion
  R1. L'inventaire est annuel et porte sur une année validée (2000-2100).
  R2. Le reste est calculé à partir des mouvements de l'année, l'existant
      initial par article n'étant pas historisé.
  R3. La consultation des états est réservée aux rôles habilités (dépositaire,
      comptable, et profils autorisés par `assertCanReadRapports`).
  R4. Un article sans mouvement apparaît tout de même dans l'inventaire, avec
      des quantités nulles, car il existe en base.

Résultat attendu
  L'état d'inventaire présente, par nomenclature puis par article, les
  quantités et valeurs d'entrée, de sortie et de reste pour l'année choisie,
  avec export PDF et Excel. Les pertes et les retours ne produisent aucun
  résultat, faute d'implémentation.

Limites à signaler explicitement
  - Absence totale du circuit de retour de matériel (aucune route, aucun
    écran, aucun mouvement).
  - Absence de déclaration et de suivi des pertes, malgré la page déclarée dans
    la configuration des rôles.
  - Inventaire limité à un état calculé : pas de comptage physique, pas de
    rapprochement, pas de clôture.
  - Les pages `pertes` et `inventaire` étant absentes du menu, un utilisateur ne
    peut pas les atteindre depuis l'interface, même si sa configuration de rôle
    les autorise.

C. EXPLICATION
--------------------------------------------------------------------------------

Journal des mouvements (backend)
  - L'API ne possède qu'une route de lecture : `GET /api/mouvements` et
    `GET /api/mouvements/:id` (idem `findOne`). Aucun `create` / `update` / `delete`
    n'est exposé — le contrôleur `mouvement.js` interdit explicitement **toutes**
    les opérations d'écriture (extrait 11.2 : retour HTTP 405 « Cette méthode n'est
    pas autorisée »). Le journal est donc un état en lecture seule, alimenté par
    les autres modules.
  - La lecture est protectée pour le demandeur : si le rôle de l'utilisateur
    connecté est `DEMANDEUR_ROLE`, `securePopulateAndFilters` restreint
    l'affichage des mouvements à ceux liés à sa demande (extrait 11.1). Les
    autres rôles voient le journal complet. `getRoleCode` (utils/roleGuard.js,
    lignes 27-40) mappe le compte Strapi sur les codes de rôles validés par
    `APP_ROLES`, et `assertCanWrite` (lignes 57-72) protectiona les mutations
    restantes (ajout d'entrée, réception, sortie...).
  - `findMouvements` dans `sortie.js` (lignes 1381-1411) permet de lister les
    mouvements d'un ordre de sortie donné, et n'autorise la lecture que pour le
    demandeur de cet ordre — une autre piste d'audit, aussi restreinte.

Journal des mouvements (frontend)
  - L'écran « Journal comptable » (`Journal.tsx`, extrait 11.3) est le seul
    chargement réel : il appelle `fetchEntrees` et `fetchSorties` en parallèle,
    fusionne les réponses en une liste de mouvements, et gère proprement les
    cas d'échec réseau en conservant les tableaux vides et un message d'erreur
    au lieu de replier sur des données fictives. C'est l'exemple de conformité
    au cycle de vie : la lecture est authentiquement rattachée à l'historique
    des opérations.
  - Les écrans « Mouvements » et « Mes mouvements » ne sont pas reliés à
    l'API : `Movements.tsx` filtre localement un tableau `mockMovements`
    (extrait 11.5, lignes 110-118) et `MyMovements.tsx` initialise son état
    avec ce même tableau (`useState(mockMovements)`). Leurs filtres (type,
    statut, date, recherche) s'appliquent sur des données fictives — un
    résultat de démonstration ou d'illustration, non un état métier.
  - Leurs filtres sont sémantiquement restreints (type `entry|exit`,
    statut `pending|approved`, fenêtre horaire, recherche par référence),
    ce qui donne parfois une illusion d'historique, mais les données ne sont
    jamais actualisées.

Reddition de compte (frontend)
  - `Reports.tsx` (extrait 11.4) présente une liste de rapports d'interface
    dont l'export n'est pas branché : `handleExport` ne génère ni PDF ni Excel,
    il ouvre simplement l'aperçu du rapport sélectionné. La production
    réelle de fichiers sépare la section « Reddition de compte » :
    `lib/reddition.ts`, 149-184, centralise les appels aux six routes de
    `backend/src/api/rapport` (extrait 10.1) — `recapitulation`, `recapitulations`,
    `etat-appreciatif`, `inventaire`, `grand-livre`, `bordereau`.

  - `RedditionSection.tsx` (lignes 101-131) est l'interface de saisie de l'année
    et de sélection d'article, puis charge chaque état par onglet. L'espèce
    « Grand-livre » s'appuie sur l'état d'inventaire pour proposer un article
    par défaut, et la section expose les boutons `exportPdf` / `exportExcel`
    qui s'appuient sur `lib/reddition.ts` (149-184) pour appeler les routes
    correspondantes.

  - La section est réservée aux rôles `depositaire` et `comptable` : `peutVoir`
    (ligne 133) teste l'appartenance aux rôles autorisés, et renvoie `null` si
    l'utilisateur ne relève pas de ces rôles, de façon complémentaire au
    contrôleur serveur `getRoleCode`.

Données manipulées
  - Backend : mouvements (référence, type, date, utilisateur, action, matériel,
    quantité, statut, sortie liée, observations), utilisateurs et leurs rôles.
  - Frontend : réponses `fetchEntrees` / `fetchSorties` depuis l'API, tableaux
    `mockMovements` pour les écrans démonstratifs.
  - Résultat : journal fusionné type entrée/sortie, listes par ordre de sortie
    (profil demandeur), notes d'audit.

Règles de gestion
  R1. Le journal n'accepte aucune écriture (405 systématique).
  R2. Le demandeur ne voit que les mouvements de sa demande (sécurité côté
     lecture).
  R3. La lecture complète du journal est réservée aux autres rôles (dépositaire,
     comptable, etc.).
  R4. Les écrans simulés filtrent des données locales ; ils ne reflètent pas
     l'état réel du système.
  R5. L'export de reddition est délégué à la section « Reddition de compte » ;
     l'écran `Rapports` n'exporte rien d'objet.

Résultat attendu
  Un journal des entrées et sorties reconstituable, filtrable, avec audit par
  ordre de sortie et note d'utilisateur. Le rendu actuel du projet est partiel :
  l'historique réel n'est accessible que depuis le journal (backend), tandis que
  les écrans « Mouvements » et « Mes mouvements » restent des démonstrations.

Limites à signaler explicitement
  - Le journal est en lecture seule : aucune route de création, de modification,
    de correction ou de suppression n'existe.
  - `Movements.tsx` et `MyMovements.tsx` ne lisent rien de l'API.
  - `Reports.tsx` ne produit pas d'export de fichier.
  - La section Reddition n'est accessible qu'aux profils `depositaire` et
    `comptable`.
  - Il n'existe pas de page/publier d'acte de reddition officiel : la
    reddition se fait par des états de rapports consultables.

D. CAPTURE D'ÉCRAN RECOMMANDÉE
--------------------------------------------------------------------------------
  Écran « Journal Comptable », avec la liste des entrées puis des sorties
  reconstituée après chargement (pas de données fictives dans le chargement
  principal, contrairement aux écrans « Mouvements » et « Mes mouvements »).
  Pour la reddition : l'onglet « Grand-livre » de la section Reddition de
  compte après sélection d'un article, avec les boutons d'export PDF et
  Excel.


================================================================================
 12. CONCLUSION
================================================================================

Ce chapitre a livré l'analyse du code réel du dépôt `Compta-main` (React 18
frontend, Strapi 5 backend, PostgreSQL) pour les onze fonctionnalités
étudiées. La règle de départ de ce travail était d'identifier, dans le code,
ce qui existe, comment il fonctionne et jusqu'où il résiste aux exigences du
cahier des charges. Les constats sont homogènes : le quotidien est
mise en œuvre avec précision, les coins philosophiques du système restent
vide.

SYNTHÈSE DES RÉSULTATS PAR FONCTIONNALITÉ

  1. DEMANDE DE SORTIE
     - Implémentée : formulaire de demande avec état en base ; validation
       propre d'un profil (signature 3) au contrôleur de la demande.
     - Limite : la validation n'est pas séparée de la préparation — le
       magasinier prépare le matériel avant la validation, contrairement à la
       règle du cahier des charges.

  2. SIGNATURE
     - Implémentée : procédure en 3 étapes avec dépôt successif, pointage
       du contenu, et vérification que la signature est bien validée.
     - Limite : l'antécédent d'une signature n'est pas retenu dans le code
       analysé, mais la première étape du signalétique reste indéterminée.

  3. SIGNATURE 3 (CONTRÔLE D'APPROBATION)
     - Implémentée dans `sortie.js` : transaction du contrôleur, réception du
       document signé, enregistrement de l'auditeur, libération du
       réservoir et impression du bon.
     - Limite : l'audit de la transaction (who/when) n'est pas capturé
       sous forme de journal explicite.

     (voir 1 = arrivée, 3 = signature, 6 = validation, 7 = préparation,
     11 = sortie, 4 = réception, 5 = remise, 8 = remise détenteur,
     9 = distribution, 10 = inventaire)

  4. RÉCEPTION
     - Implémentée : page de réception physique avec formulaires de quantité
       et validation, stock actualisé après validation.
     - Limite : route `/api/receptions-physiques` (frontend) ne porte que sur
       la réception physique ; la réception "lignes" (quantité)
       n'est pas accessible depuis l'interface.

  5. REMISE PHYSIQUE
     - Implémentée : `sortie.remise` propre, avec consentement explicite du
       magasinier.
     - Limite : le matériel est marqué « remis » alors que la règle
       exige un état « prêt » avant la remise au détenteur, le
       remis-à-partir du stock n'est pas géré.

  6. VALIDATION
     - Implémentée : validation de la demande seulement après signature.
     - Limite : la préparation-contrôle a lieu avant la validation, ce qui
       va à l'encontre de la règle « le magasinier prépare après
       validation ».

  7. PRÉPARATION
     - Implémentée : vérification du stock, placement du matériel en
       attente, filtrage des étapes (validation, réception, remise).
     - Limite : `PreparationOrdreSortie.tsx` récupère le panier et les
       articles par API, mais n'affiche pas les quantités libérées.

  8. PRÉPARATION DU STOCK (réservoir = stock)
     - Implémentée dans `sortie.js` : assertion de disponibilité, réservation
       du stock, et libération à la signature.
     - Limite : le contrôleur effectue la réservation dans une session
       non-transactionnelle, ce qui ouvre la porte à un risque de
       concurence.

  9. DISTRIBUTION AU DÉTENTEUR
     - Implémentée : `remise-detenteur.js` avec `conforme` et `anomalie`,
       date de réservation, et réponse `existantQ` (quantités compris
       entre 0 et stock).
     - Limite : l'affectation au détenteur n'est possible que si la
       réception a rapporté une quantité positive (`quantite_recue > 0`),
       ce qui n'est pas le cas lors d'une réception vide ou anomalie.

  10. RETOURS, PERTES ET INVENTAIRE
      - RETOURS : non implémentés du tout (aucune route, écran, ou mouvement
        inverse). Circuit de retour de matériel absent du système.
      - PERTES : non implémentés (page `pertes` déclarée dans
        `ROLES_CONFIG` mais absente du menu et sans module).
      - INVENTAIRE : partiellement implémenté : état de reddition calculé
        (`calculerInventaire`), mais sans comptage physique, sans rapprochement,
        et l'écran `inventaire` n'existe pas dans le menu.

  11. JOURNAL DES MOUVEMENTS
      - Implémenté en lecture seule : aucune route d'écriture sur
        `mouvement` (405 systématique). Le `Journal` charge les données par
        API, les écrans « Mouvements » et « Mes mouvements » utilisent des
        données fictives. `Reports.tsx` ne produit pas d'export.

BILAN GLOBAL
  - Les 11 fonctionnalités présentées se lisent en deux groupes : un
    couche de quotidien fort structurée (demande, signature, réception,
    remise, validation, préparation, distribution) et un couche de clôture
    (retours, pertes, inventaire, journal, reddition) largement
    partielle.
  - Les principaux risques identifiés : pas de transaction de réservation
    (concurrence), non-respect du calendrier de signature (préparation
    avant validation), circuit de retour absent, inventaire calculé sans
    comptage saisi, écrans de démonstration (mouvements) qui ne sont pas
    reliés à l'API.
  - Les risques opérationnels sont multiples : le journal ne peut être
    corrigé, les retours ne sont pas tracés, et l'inventaire annuel ne
    permet pas de construire un bilan de stock.

VERIFICATION DE VALIDITÉ DU DOCUMENT
  - Tous les extraits cités sont issus de fichiers lus dans le dépôt, avec
    numérotation de lignes vérifiée.
  - Aucun fichier du projet n'a été modifié ni supprimé (sauf le livrable).
  - Aucune donnée sensible (mots de passe, tokens, clés secrètes) n'a été
    reproduite ; les comptes de démonstration et leurs mots de passe ne
    sont pas reproduits.
  - Le document ne prétend pas à l'exhaustivité ; il signale honnêtement
    les fonctionnalités absentes.

CONCLUSION
  Le projet `Compta-main` est fonctionnel sur le quotidien de gestion de
  stock, mais la conception restreint les aspects du cycle de vie qui
  exigent un suivi strict : retour de matériel, déclaration de pertes et
  inventaire physique. Le mémoire doit donc distinguer ce qui est
  exploitable tel quel des comportements à corriger avant déploiement :
  séparer la préparation de la validation, sécuriser la réservation par
  transaction, rendre accessible l'inventaire et les pertes, et relier
  les écrans « Mouvements » à l'API.
